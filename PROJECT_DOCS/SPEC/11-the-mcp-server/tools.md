### Tools

- **The tools** are `write`, `query`, `build`, `score`, `status`, `cancel`, `build-trail`, `verify`, `update-format`, `export-latex`, `init`, `configure-providers`, `configure-models`, `models`, `show-config` and `probe`. Every tool but `query` and `write` is one subcommand, named as the subcommand.
  - `query` is a **family tool**: one MCP tool with an `operation` argument that names one of several subcommands, each an operation of the tool. Its operations are the queries `citations-of`, `edges`, `find`, `show`, `stats` and `trace`.
  - `write` runs a batch whose entries name the write ops ([§8](../8-maintenance-subcommands/write-batches/index.md)); a write op has no tool of its own.
  - Each operation stays a subcommand, unchanged on the command line.
- **CLI-only commands.** Every other subcommand is served. These are not, and no tool exposes them:
  - `auth` and its subcommands: a key arrives on stdin and leaves on stdout, neither of which a tool call has, and no tool accepts or returns a key;
  - `wait`: a tool call would hold the turn for the build's or score run's duration, so a session polls `status` instead;
  - `mcp`, the server itself;
  - `help` and `completion`, which belong to the CLI framework.

  The root help and `mcp`'s help name `auth`, `wait` and `mcp` as the CLI-only commands ([Served text](served-text.md)).
- **A command tool's input schema** has one property per positional and per flag of its command, named as the command line names them without the dashes. The global flags are excluded, since the server has its own, except `project-dir` ([Two modes](two-modes.md)). A duration flag's argument is the Go duration string the command line takes (`30s`). A flag is optional in the schema unless its command declares it required, as `trace`'s `direction` is. A command tool's argument whose values are a fixed set, a mapping key's included, has them as its property's `enum`. Where an argument also accepts an alias of a value, as `build`'s `through` accepts a stage's display name, the `enum` lists the canonical values alone; the alias is the command line's, and the command's MCP note says so ([Served text](served-text.md)). Each property's description but `project-dir`'s is the argument's brief, a few words naming what the value is, at most 60 characters; `project-dir`'s is the one [Two modes](two-modes.md) gives it. The `write` and `query` tools' properties, and the sub-properties of a mapping such as `score`'s `edge`, are not briefs. The argument's full description — a positional's as its command declares it; a flag's usage, followed by the default `--help` prints for the flag where it prints one and, for a duration flag, by the note that its argument is a Go duration — is in the help's argument list ([Served text](served-text.md)).
- **The `query` tool's schema** has `operation`, required, a string enum of its operations' names, and `arguments`, an object holding what the operation takes: its positionals and flags by name, derived as a command tool's schema is, but described by the operation's help alone, with no brief. `operation`'s description names where each operation's help is, and `arguments`' names that help's argument list. The tool checks `arguments` against the operation's own schema: an unknown key, a missing required key or a value of the wrong type is a refusal, `refused`, one item per fault, `check: usage`, `key` the argument's name, `allowed` every argument the operation takes, and `remedy` naming `allowed` for the argument names and the operation's help resource for what the operation does. A fault inside a mapping argument is named at its dotted path (`edge.relation`), its `allowed` the mapping's keys. An `operation` outside the enum, or an `arguments` that is not an object, fails the tool's schema.
- **The `write` tool's schema** is the batch: `entry`, required, an array of objects, each naming its op under `operation` beside that op's keys; and `dry-run` and `commit`, booleans. The schema gives an entry's keys no types. The batch checks the entries' shape ([§8](../8-maintenance-subcommands/write-batches/index.md)), every fault an item naming its `entry`, and a wrong value for a key is the op's own refusal ([§8](../8-maintenance-subcommands/index.md)), which names the key and, where the value comes from a fixed set, lists that set as `allowed`.
- **Every tool's schema** has one more property, `project-dir`, the project the call runs in ([Two modes](two-modes.md)).
- **Results.** A tool's result is the [§7](../7-tool-result-contract-and-exit-codes/index.md) result ([§7](../7-tool-result-contract-and-exit-codes/tool-results.md)), as the result's text and as structured content. `isError` is set exactly when the result's exit code ([§7](../7-tool-result-contract-and-exit-codes/index.md)) is not 0, so a refusal reaches the model as an error with its items and remedy, while `bounded` and a completed `cancel` do not. A refusal's items are defined in [§7](../7-tool-result-contract-and-exit-codes/item.md), `line` and `column` included. Arguments that fail the tool's schema (a missing required key, a wrong type, an unknown key, a value outside a property's `enum`) are JSON-RPC `-32602` errors, not refusals; a `query` tool's `arguments` are checked as above instead. A list query answers completely, or is sliced by `limit` as [§7](../7-tool-result-contract-and-exit-codes/bounded-results.md) states.
- **Read-only annotation.** The read-only tools have the read-only annotation: `query`, `verify`, `status`, `build-trail`, `show-config`, `models` and `probe`. A family tool is read-only where every operation is.
- **Descriptions.** A tool's description, and the help it points to, are defined in [Served text](served-text.md).
- **`build` and `score` are detached.** A call starts `kbase build` or `kbase score` as a process of its own, from the root of the call's project, passing `--project-dir` where the call named one, in its own process group, with no stdin, configured as the server is (the environment, `--config-dir`, `--log-level` and `--log-file`, [§9](../9-configuration/index.md)). The run's stdout and stderr are captured as files in the state store's `reports/` ([§6](../6-build-state-ledger-and-monitoring/index.md)); the capture files are pruned as [§6](../6-build-state-ledger-and-monitoring/index.md) states. A relative `state-dir` argument resolves against the repository root; the server's own `--config-dir` and `--log-file` stay relative to the server's working directory. Where `status` would refuse (no git worktree, or a `--state-dir` inside `kb-root/`), the tool returns that refusal and starts no process. A run starting during a write waits that write out before its first stage (`build`) or its first rebuild of the derived views (`score`), and is visible to `status` while it waits.

  Before starting the run, the tool reads the configuration as the run will, from the same files, flags and environment ([§9](../9-configuration/index.md)). That read decides nothing: it refuses nothing, writes nothing and resolves no role, and the run reads its configuration again. Each fault it finds, a configuration that fails to load included, is an item of the `warnings` of the tool's `done` result below, `[]` where there is none. The tool's own refusals, `status`'s above and `edge`'s below, come before that read and carry `warnings: []`.

  The tool waits at most 5 s, until the run has started or has exited, and returns by what happened first:
  - *started*: outcome `done`.
    - `build` has entered a stage, as its progress record shows. The result has `kb-root`, `state-dir`, `pid`, `resume`, `wait` and `warnings`; `resume` is absent where the record's command does not parse as a `kbase build` invocation ([§6](../6-build-state-ledger-and-monitoring/index.md)).
    - `score` has its ledger and pid. The result has `kb-root`, `state-dir`, `pid`, `run`, `ledger`, `wait` and `warnings`.
  - *exited*: the run's own result, `isError` set by its outcome ([§7](../7-tool-result-contract-and-exit-codes/index.md)).
  - *still starting at the bound*: outcome `done` with `kb-root`, `state: starting`, `state-dir`, `pid`, `wait` and `warnings`. The run keeps running, and `status` follows it.

  `wait` is the shell command that runs the server's own executable as `wait [--project-dir <root>] --state-dir <store> --pid <pid>`, with `--project-dir` where the call named one, shell-joined as `status` joins its `resume` ([§6](../6-build-state-ledger-and-monitoring/index.md)). It returns when the run is over and prints the run's result: for a build, the store's `status` result; for a scoring run, the run's own stored result ([§6](../6-build-state-ledger-and-monitoring/kbase-wait.md)), so a session runs it in the background and is woken when it exits. `status` and `cancel` follow the start.

  `score`'s `edge` argument is a mapping of `source`, `target` and `relation`, each a required string and no other key allowed, which the run receives as `--edge <source>,<target>,<relation>`. A value holding a comma is refused at `edge`, `check: usage`, and starts no process.
- **`build-trail`** is a read-only tool; its result, refusals and commands are defined in [§6](../6-build-state-ledger-and-monitoring/kbase-build-trail.md).
- **What the server never does.** It sends no sampling request and offers no prompts. No inference runs from any tool but `build`, `score` and `probe`, and each tool's inference is its own: the build's decision and text calls, the score run's scoring calls, the one call `probe` makes. `models` reads the selected provider's model catalogue; `configure-providers` reads the catalogue of the entry it writes where a key is stored for it; `configure-models` checks each reference it writes against its provider's catalogue. None of them makes a model call. The server writes nothing but JSON-RPC frames to stdout; diagnostics go to stderr and `--log-file`. It loads no configuration itself: the verbs it exposes load their own on each call ([§9.3](../9-configuration/9.3-strict-load-contract.md)), and a `build` or `score` launch reads a run's only to report it.
- **Protocol.** The server implements one MCP revision, `2025-11-25`. An `initialize` naming another revision is answered with the server's, for the client to decide. Calls are answered one at a time, in order. EOF on stdin ends the server.
