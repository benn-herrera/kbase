#### One write lock

A write batch and `update-format` hold the KB write lock for the whole run: from loading the KB to the result, the rebuild of the derived views included. `init` holds it from before `kb-root/` exists — the lock sits on the directory that contains `kb-root/`, so it is available at creation — through the scaffold, the final rebuild and the initial commit to the result. `score` takes it around writing its results — every value the run produced, after the item loop — and around its rebuild at the start, never across the run ([§8](../score/writing-the-results.md)).

A writer that cannot take it within 30 s gets `retry` with `check: lock`, `path` the repository root, and the remedy. A write verb probes for a run holding the run lock ([§6](../../6-build-state-ledger-and-monitoring/git-holds-the-recoverable-record.md)) before it waits on the write lock and again after taking it: where one runs, the verb is `refused` with the `lock` item at once, taking no wait. A build waits out a write in progress, up to the same 30 s, before it writes (`retry` if it cannot); its own writes take no KB write lock. A scoring run's own writes make no run-lock probe, writing as the run that holds it. `verify` and the queries take no lock. On Windows no advisory lock exists ([§6](../../6-build-state-ledger-and-monitoring/index.md)): neither the `retry` nor the run-running refusal is available there, and the operator must keep to one writer at a time.
