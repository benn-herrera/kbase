**Design:**
- [§4.2 Tool descriptions, help resources and `--help`](../../NEW_MCP_CLI_DESIGN/4-served-text/4.2-tool-descriptions-and-help.md) — "one shared help body, the same text on both
  surfaces except that each names an argument as that surface takes it: `--name` at the command
  line, `name` over MCP", and the renderings table
- [§2.8 Results and exit codes](../../NEW_MCP_CLI_DESIGN/2-conventions/2.8-results-and-exit-codes.md) — "over MCP, the same document as text and as structured content"
- [§3 Operations](../../NEW_MCP_CLI_DESIGN/3-operations/index.md) — the surfaces: a query op is "over MCP, an op of the `query` tool, taking
  `operation` and `arguments`"

Relies on O and P: their help bodies and refusals are among the texts this package marks. That
includes P's `cmd/trace.go`, beside `cmd/edges.go`.

**What must hold** (the mechanism inside these bounds is the coder's):
1. **One marker, and the marked form.** Text names a tool argument through one marker, defined
   once.
   - The marker tells a flag from a positional.
   - An example call (item 4) is marked the same way, as an arguments mapping.
   - **The marked form** is text or a value carrying markers, not yet spelled for a surface. This
     leaf uses that term for it throughout.
   - The author writes the marker explicitly. It is never inferred from a `--x` or `<x>` shape,
     because angle brackets are also placeholders that stay as written: `<id>` in
     `cmd/add-citation.go:25` (`["<snippet>"](<path>#<anchor> "<id>")`), `run-<id>` at
     `cmd/score.go:503`, `<entry>/<id>` (`cmd/configure.go`, `internal/config/configure.go`),
     `<provider>/<model>` (`cmd/score.go:480`, `cmd/probe.go`) and `<state-dir>/score/<run>/`
     (`cmd/score.go:497`).
   - The marker's home imports no kbase package. The refusal producers in `internal/{kb,build,buildstore,config,query,score,statedir,write}`
     all reach it.
2. **One spelling per surface.** A flag is `--name` at the CLI and `name` over MCP. A positional
   is `<name>` at the CLI, as its usage line spells it (`mcp.DeclaredPositionals`), and `name` over
   MCP.
   - Each surface's spelling is one function, and that same function spells help texts and result
     documents.
   - No other code spells a marked argument.
   - No code rewrites a literal `--name` in text into `name`. Reading a recorded argv with the
     command's own flag set (item 5) parses the argv; it does not rewrite text.
3. **What is marked: the classification rule.**
   - **A tool argument is marked** wherever text an MCP reader can receive names it. A tool
     argument is any flag `mcp.CommandSchema` makes a property, `project-dir` included, and any
     positional. The texts:
     - `Short`, the shared body `Long`, and the MCP note;
     - a family's `Summary` and `Help`;
     - a flag's usage string, which is both the CLI usage block and the MCP schema description
       (`internal/mcp/mcp.go:557`, `property.Description = f.Usage`);
     - an item's `key`;
     - the argument that a `detail`, a remedy or a result field's prose names (for example the
       `note` at `internal/build/build.go:598`).
   - **A `kbase …` command line is an example call** (item 4), whether in help, in a result field
     such as `resume`, or in a remedy, prose-embedded ones included ("kbase find lists the nodes
     that stand").
     - Where a tool binds the command, it renders over MCP as that tool's call. The call carries
       only the arguments that tool's schema has. A flag it does not take, such as the server's
       own `--config-dir`, is left out over MCP.
     - Where no tool binds the command (a `cliOnly` command, which a person runs at a shell), it
       stays a CLI line on both surfaces.
     - A non-kbase command (`git init`, `pandoc --version`) is never rendered.
   - **Literal `--name` stays** in these cases:
     - a flag no tool's schema carries: the server's own `--config-dir`, `--log-level` and
       `--log-file`, and every flag `mcp.ExcludeFlag` excludes;
     - text no MCP rendering reads: a CLI note, the root's `Long`, the text of a `cliOnly` command,
       and the `kbasedev` replay files;
     - a producer on a path no tool call reaches may stay literal; marking it is harmless.
4. **How an example call renders.** The example is held as the command and an arguments mapping
   (MCP `arguments`), never as a written command line. The renderer reads which tool binds the
   command, and whether that tool is a family, from the command tree's annotations. It holds no
   copy of that table.
   - **At the CLI** it renders as `kbase <command>` everywhere, help included: a help example is a
     line a reader pastes at a shell, where a bare `find` runs another program. Then come `mcp.CommandLine`'s positionals and `--name value` per flag in name order. That
     is the one function that already turns tool arguments into a command line
     (`internal/mcp/mcp.go:620`).
   - **Over MCP** it renders as the tool's name, one space, then the call's arguments as compact
     JSON.
     - A family member's call is `{"operation":"<op>","arguments":{…}}`, with `operation` first.
     - A command's own tool's call is `{…}`.
     - Argument keys are sorted, and values are typed as the tool's schema types them.
   - **stats.** The literal `find` in stats' `Long` before each example goes (`cmd/stats.go:23–25`),
     because the rendering names the command. The arguments mapping leaves `Limit` out, as
     `findArgs` does: "its limit left out" (`cmd/stats.go:37–39`). The two examples render:
     - over MCP, as
       `query {"operation":"find","arguments":{"kind":["claim"],"max":0.65,"min-dependents":1,"order":"descending","sort":"dependents"}}`
       and `query {"operation":"find","arguments":{"kind":["claim"],"min":0,"sort":"strength"}}`;
     - at the CLI, as `find --kind claim --max 0.65 --min-dependents 1 --order descending --sort dependents`
       and `find --kind claim --min 0 --sort strength`.
   - **build's resume.** The `resume` (`build.go:752`) renders over MCP as
     `build {"no-inference":true,"resume":true,"state-dir":"…"}`, with the arguments the run
     carried.
5. **The marked form crosses every boundary.** A `result.Item` value, in memory or recorded, holds
   the marked form. It is spelled only where a document or a help text is emitted.
   - `status` emits a run's recorded items again (`recent-refusals`,
     `internal/buildstore/status.go:264`) and its recorded `Resume` argv
     (`internal/buildstore/store.go:164`, rendered through `RecordedCommand`, `status.go:349`). It
     spells both for the surface reading it. The argv is read with build's own flag set into an
     arguments mapping.
   - Items an earlier kbase recorded keep their literal spelling. They are not converted.
   - **No state-store version bump.** `internal/buildstore/storeformat.go:14–15` defines the
     version as "the store's layout version: the names of its files and the shapes of the records
     in them". A marker inside the string fields `Items[].key`, `detail` and `remedy`
     (`store.go:171`) changes neither, and `Resume` stays a `[]string` argv.
     `buildstore.StoreFormat` stays 1 ([SPEC §6](../../PROJECT_DOCS/SPEC/6-build-state-ledger-and-monitoring/the-state-store-is-versioned.md)). A package that records an
     arguments mapping instead of the argv changes a record's shape and bumps the version, and
     that is not this package.
6. **The surface is the call's, never the process's.** One test process runs both surfaces
   (`kbase(t, …)` runs `rootCmd` in-process, `cmd/resultdocs_test.go:23`), and `kbase mcp` serves
   tools in-process.
   - A launched run is a CLI process whose own document reaches an MCP caller
     (`internal/mcp/launch.go:203`, `_, err = out.Write(doc)`).
   - So `Launch.start` tells the child its document is read over MCP. The child reads that signal
     where the CLI settles its surface: `cmd/main.go` (`rootCmd`, `PersistentPreRunE` at `:87`), or
     where the coder places it.
   - The signal is no property of any tool's schema.
7. **A cheap expectation check at the MCP boundary.** Where a tool's result is composed, an item
   whose `key` is `--<p>` or `<p>`, for an argument `p` of that tool, is logged at warn through the
   server's logger. It catches a producer the marker missed. It logs only and rewrites nothing.
8. **`listQueryHelp`'s two spelling parameters go.** `listQueryHelp(limit, offset string)`
   (`cmd/query.go:130`) is today's one per-surface mechanism: callers pass `"--limit", "--offset"`
   (`cmd/main.go:74`) or `"limit", "offset"` (`cmd/surface.go:53`), and it derives `sort` and
   `order` by `strings.TrimSuffix(limit, "limit")`.
   - It becomes one marked text that both callers share.
   - The parameters go in this package, after the structural test (Tests) shows the marked text
     rendering both forms.
   - `buildstore.ProjectRoot(path, key string)` (`internal/buildstore/status.go:371`) takes its key
     per surface the same way: `cmd/mcp.go:25` passes `"--project-dir"` and
     `internal/mcp/mcp.go:443` passes `projectDirProperty`. Its `key` parameter goes once both
     callers pass the marked `project-dir`.
